# NoSQL vs SQL — когда что выбирать

## Это не религия

Выбор БД — инженерное решение, а не идеологическое. У каждого типа есть свои 20% задач, где он сияет, и 80% — где он хуже альтернатив.

## Дерево решений

```
Нужны сложные JOIN'ы и отчёты?
├── Да → Реляционная БД (PostgreSQL / MySQL)
└── Нет → Данные — граф? (соцсеть, рекомендации)
    ├── Да → Neo4j / ArangoDB
    └── Нет → Данные — документы с гибкой схемой? (каталог, контент)
        ├── Да → MongoDB / Couchbase
        └── Нет → Нужен быстрый кэш? (сессии, счётчики)
            ├── Да → Redis
            └── Нет → Огромные объёмы записи? (IoT, логи, временные ряды)
                ├── Да → Cassandra / ScyllaDB
                └── Нет → Полнотекстовый поиск?
                    ├── Да → Elasticsearch
                    └── Нет → Возьми PostgreSQL — не ошибёшься
```

## Сравнительная таблица

| Критерий | PostgreSQL | MongoDB | Cassandra | Redis | Neo4j | Elasticsearch |
|----------|------------|---------|-----------|-------|-------|---------------|
| **Модель** | Реляционная | Документы | Wide-Column | Key-Value | Граф | Поисковая |
| **Транзакции** | ACID | Multi-doc | Lightweight | Нет* | ACID | Нет |
| **JOIN'ы** | Да | $lookup (неэффективно) | Нет | Нет | Обход графа | Нет |
| **Масштабирование** | Вертикальное + read реплики | Горизонтальное (шарды) | Горизонтальное | Кластер | Read реплики | Горизонтальное |
| **Гибкость схемы** | ALTER TABLE | Schema-less | Гибкая | Schema-less | Гибкая | Гибкая |
| **Сложные запросы** | SQL (полный) | Aggregation Pipeline | CQL (ограничен) | Команды | Cypher | Query DSL |
| **Когда выбирать** | Почти всегда default | Гибкая схема, документы | IoT, временные ряды | Кэш, сессии, счётчики | Соцсети, рекомендации | Полнотекстовый поиск, логи |

*Redis — транзакции только в рамках MULTI/EXEC, без отката при падении.

## Антипаттерны выбора

### MongoDB для всего
- ❌ «MongoDB — круто, давай всё туда»
- ✅ MongoDB хорош для документов с гибкой схемой; плох для отчётности с JOIN'ами и агрегациями

### NoSQL потому что «SQL тормозит»
- ❌ «У нас много данных, SQL не справится!»
- ✅ PostgreSQL с правильными индексами и партиционированием тянет миллиарды строк. Проблема в индексах, а не в SQL.

### Cassandra для ad-hoc аналитики
- ❌ «Положим все данные в Cassandra и будем строить дашборды»
- ✅ Cassandra — под конкретные паттерны доступа. Ad-hoc запросы (WHERE по не-ключу) умрут.

### Одна БД для всего
- ❌ «У нас PostgreSQL для всего: и транзакции, и поиск, и кэш, и аналитика»
- ✅ Правильный стек: PostgreSQL (основные данные) + Redis (кэш) + Elasticsearch (поиск) + ClickHouse (аналитика)

## Полиглотная персистентность (Polyglot Persistence)

Современные системы используют **разные БД для разных задач**:

```
Приложение
├── PostgreSQL  — основное хранилище, транзакции
├── Redis       — кэш, сессии, rate limiting
├── Elasticsearch — полнотекстовый поиск
├── ClickHouse  — аналитика (OLAP)
└── S3/MinIO    — файлы, бэкапы
```

## Практический совет

Начинай с **PostgreSQL**. Он покрывает 90% задач. Когда реально упрёшься в ограничения — подключай специализированные БД. «Premature optimization is the root of all evil» работает и для выбора БД.
