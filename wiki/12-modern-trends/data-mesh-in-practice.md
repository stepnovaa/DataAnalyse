# Data Mesh на практике

## Не путай с технологией

Data Mesh — **организационный** паттерн, а не технологический. Нельзя «купить Data Mesh». Можно купить self-serve платформу, но без изменения культуры это бесполезно.

## Когда Data Mesh имеет смысл

- 10+ независимых бизнес-доменов
- 50+ дата-инженеров/аналитиков
- Центральная data-команда — бутылочное горлышко
- Бизнес-домены хотят autonomy над своими данными

## Когда НЕ имеет смысла

- < 50 человек в компании
- Одна data-команда справляется
- Нет зрелой data-культуры (сначала наведи порядок в одном DWH)

## Дорожная карта внедрения

### Фаза 1: Платформа

- Self-serve инфраструктура (каталог, lineage, качество, деплой)
- Домены могут создавать data products без участия центральной команды

### Фаза 2: Первый домен

- Выбери самый мотивированный домен
- Помоги выделить data product owner'а
- Поддерживай, не бросай

### Фаза 3: Масштабирование

- Ещё 2-3 домена
- Federated governance: общие стандарты, локальная автономия
- Обмен опытом между доменами

### Фаза 4: Оптимизация

- Метрики здоровья data products
- Cross-domain data products
- Автоматизация compliance

## Data Product — чек-лист

Хороший data product:
- [ ] Документирован (что, зачем, как использовать, SLA)
- [ ] Доступен через каталог (легко найти)
- [ ] Имеет владельца (кто ответит на вопросы в 2am)
- [ ] Протестирован (качество данных проверяется)
- [ ] Версионирован (изменения не ломают потребителей)
- [ ] Имеет SLA (свежесть, полнота)

## Антипаттерны

- **Data Mesh без платформы**: домены изобретают велосипеды → хаос
- **Только технология**: купили DataHub, не поменяли ownership → старый bottleneck
- **Слишком рано**: 3 дата-инженера строят data mesh → overhead > пользы
- **Без governance**: домены делают что хотят → data swamp, а не mesh

## Real-world примеры

- **Zalando**: первопроходцы, открыли свои практики
- **Netflix**: data mesh для разных content verticals
- **Spotify**: domain-oriented data ownership
