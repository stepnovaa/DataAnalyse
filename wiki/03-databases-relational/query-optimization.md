# Оптимизация запросов

## Системный подход

Оптимизация запроса — не магия, а методичный процесс:

1. **Измерь** текущую производительность
2. **Найди** узкое место (EXPLAIN ANALYZE)
3. **Исправь** одну вещь
4. **Перемерь**
5. Повтори, пока не достигнешь цели

## EXPLAIN ANALYZE — главный инструмент

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT ...
```

Ключевые поля:
- **actual time**: реальное время (планирование + выполнение)
- **rows**: реальное количество строк vs оценка планировщика (если сильно расходится → плохая статистика)
- **Buffers: shared hit/read**: hit = из кэша, read = с диска. Много read → плохо
- **loops**: сколько раз выполнялся узел плана

## Частые проблемы и решения

### 1. Seq Scan на большой таблице

**Симптом**: `Seq Scan on large_table (actual time=5000..5000 rows=10000000)`

**Решения**:
- Создать индекс под WHERE/JOIN-условия
- Убедиться что индекс используется (не перекрыт функцией)
- Проверить статистику: `ANALYZE table_name`

### 2. Nested Loop вместо Hash Join

**Симптом**: `Nested Loop (actual rows=1000000 loops=1000)` — для каждой строки внешней таблицы сканирует внутреннюю.

**Решения**:
- Нет индекса на JOIN-колонке внутренней таблицы
- Оценка планировщика неверна → `ANALYZE`
- Принудительно: `SET enable_nestloop = off` (осторожно!)

### 3. Неправильный порядок JOIN

Планировщик может ошибаться при многих JOIN'ах:
- Перепиши запрос: самые селективные JOIN'ы первыми
- Используй CTE для изоляции сложных частей (материализуются)
- `JOIN` вместо подзапросов в WHERE — даёт планировщику больше свободы

### 4. Функции на индексируемых колонках

❌ `WHERE LOWER(email) = 'user@mail.com'` — индекс по `email` не используется
✅ Создай индекс на выражение: `CREATE INDEX ON users (LOWER(email))`

Аналогично: `date_trunc`, `COALESCE`, конкатенации.

### 5. Слишком много данных

- `SELECT *` когда нужны 2 колонки → лишний I/O
- Нет LIMIT, а в коде всё равно берёшь первые 10 строк
- Нет фильтра по дате в большой таблице

## Продвинутые техники

### Материализованные представления (Materialized Views)

```sql
CREATE MATERIALIZED VIEW monthly_stats AS
SELECT ... сложный GROUP BY с JOIN'ами ...
REFRESH MATERIALIZED VIEW monthly_stats;
```

Для отчётов, которые не требуют real-time данных.

### Партиционирование

```sql
CREATE TABLE orders (...) PARTITION BY RANGE (created_at);
```
- Быстрее SELECT по ключу партиционирования (partition pruning)
- Быстрее удаление старых данных (DROP PARTITION vs DELETE)
- В Postgres — декларативное с версии 10

### Параметры конфигурации

На уровне сессии (если глобально менять страшно):

```sql
SET work_mem = '256MB';          -- память для сортировок и хешей
SET random_page_cost = 1.1;       -- для SSD (по умолчанию 4.0 — для HDD)
SET effective_cache_size = '8GB'; -- размер системного кэша
```

## Антипаттерны

- `SELECT *` в продакшене (кроме ad-hoc запросов)
- Индекс на каждой колонке «на всякий случай» (замедляет запись)
- `ORDER BY RANDOM()` на большой таблице (перемешивает ВСЁ)
- Циклы с SQL-запросами вместо одного batch-запроса
