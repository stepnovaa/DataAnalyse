# Реляционная модель

## Основы

Реляционная модель (Кодд, 1970) — математическая модель данных, основанная на теории множеств и логике предикатов. Данные организованы в **отношения** (таблицы) с чёткой схемой.

## Ключевые понятия

| Термин | Формально | На практике |
|--------|-----------|-------------|
| Отношение (Relation) | Множество кортежей | Таблица |
| Кортеж (Tuple) | Строка отношения | Строка таблицы |
| Атрибут (Attribute) | Именованный столбец | Колонка |
| Домен (Domain) | Множество допустимых значений | Тип данных + ограничения |
| Степень отношения | Количество атрибутов | Количество колонок |
| Кардинальность | Количество кортежей | Количество строк |

## Ключи

### Первичный ключ (Primary Key)

Уникально идентифицирует каждый кортеж. Требования:
- Уникальность
- NOT NULL
- Неизменяемость (не должен меняться со временем)

**Суррогатный vs Естественный**:
- Суррогатный (`id SERIAL PRIMARY KEY`) — не имеет бизнес-смысла, стабилен
- Естественный (`email`, `passport_number`) — имеет смысл, но может измениться

> Всегда используй суррогатные ключи для внутренних нужд. Естественные — для бизнес-ограничений (UNIQUE).

### Внешний ключ (Foreign Key)

Связывает кортеж в одной таблице с кортежем в другой:
```sql
user_id INT REFERENCES users(id)
```

Обеспечивает **ссылочную целостность**: нельзя удалить пользователя, на которого ссылаются заказы.

### Составной ключ (Composite Key)

Ключ из нескольких атрибутов. Пример: `(order_id, product_id)` в таблице позиций заказа.

## Целостность данных

| Тип | Описание | Пример |
|-----|----------|--------|
| **Entity integrity** | У каждого кортежа есть PK | Не может быть NULL в PK |
| **Referential integrity** | FK ссылается на существующий кортеж | Нельзя заказ без пользователя |
| **Domain integrity** | Значения в рамках домена | Возраст ≥ 0 |
| **User-defined integrity** | Бизнес-правила | Сумма заказа > 0 |

## Операции реляционной алгебры

Реляционная алгебра — теоретический фундамент SQL:

| Операция | SQL | Описание |
|----------|-----|----------|
| σ (selection) | WHERE | Фильтрация строк |
| π (projection) | SELECT | Выбор колонок |
| ⋈ (join) | JOIN | Соединение таблиц |
| ∪ (union) | UNION | Объединение |
| − (difference) | EXCEPT | Разность |
| × (product) | CROSS JOIN | Декартово произведение |
| ρ (rename) | AS | Переименование |

## Почему реляционная модель работает

1. **Декларативность**: ты говоришь ЧТО, а не КАК (оптимизатор решает как)
2. **Независимость от физического хранения**: та же логическая схема — разное физическое представление
3. **Стандартизация**: SQL — единый язык, 50 лет развития
4. **ACID**: надёжность транзакций (см. [[../03-databases-relational/transactions-and-acid|Транзакции]])
